# Protocol Summary

This project is meant to be a permissionless way for users to swap assets between each other at a fair price. You can think of T-Swap as a decentralized asset/token exchange (DEX). 
T-Swap is known as an [Automated Market Maker (AMM)](https://chain.link/education-hub/what-is-an-automated-market-maker-amm) because it doesn't use a normal "order book" style exchange, instead it uses "Pools" of an asset. 
It is similar to Uniswap. To understand Uniswap, please watch this video: [Uniswap Explained](https://www.youtube.com/watch?v=DLu35sIqVTM)

## High

### [H-1] Incorrect fee calculation in `TSwapPool::getInputAmountBasedOnOutput` causes protocol to take too may tokens from users, resulting in lost fees 

**Description:** The `getInputAmountBasedOnOutput` function is intended to calculate the amount of tokens a user should deposit given an output token amount. However, the function currently miscalculates the resulting amount. When calculating the fee, it scales the amount by 10_000 instead of 1_000.

**Impact:** Protocol takes more fees than expected from users.

**Proof of Concept:**

<details>
<summary>Proof of Code</summary>

Add the following to the `TSwapPool.t.sol` test file

```javascript
    function test_getInputAmountBasedOnOutput_overcharges() public view {
        uint256 inputReserves = 1000e18;
        uint256 outputReserves = 1000e18;
        uint256 outputAmount = 100e18; // user wants 100 tokens out

        // Wrong calculation function
        uint256 buggyInputAmount = pool.getInputAmountBasedOnOutput(outputAmount, inputReserves, outputReserves);
        // Correct Calculation or logic
        uint256 correctInputAmount = ((inputReserves * outputAmount) * 1_000) / ((outputReserves - outputAmount) * 997);

        // Proof
        assert(buggyInputAmount > (correctInputAmount * 10)); // roughly 10x more

        console.log("correctInputAmount: ", correctInputAmount);
        console.log("buggyInputAmount: ", buggyInputAmount);
        console.log("Overcharge factor    :", buggyInputAmount / correctInputAmount);
    }
```
</details>

**Recommended Mitigation:** 

```diff
    function getInputAmountBasedOnOutput(
        uint256 outputAmount,
        uint256 inputReserves,
        uint256 outputReserves
    )
        public
        pure
        revertIfZero(outputAmount)
        revertIfZero(outputReserves)
        returns (uint256 inputAmount)
    {
-       return ((inputReserves * outputAmount) * 10_000) / ((outputReserves - outputAmount) * 997);
+       return ((inputReserves * outputAmount) * 1_000) / ((outputReserves - outputAmount) * 997);
    }
```

### [H-2] Lack of slippage protection in `TSwapPool::swapExactOutput` causes users to potentially receive way fewer tokens

**Description:** The `swapExactOut` function does not include any sort of slippage protection. This function is similar to what is done in `TSwapPool::swapExactInput` where the function specifies a `minOutputAmount` they are willing to receive for their `inputAmount`, the `swapExactOutput` function should also specify a `maxInputAmount` the user is willing to give for their `outputAmount`.

**Impact:** If market conditions change before the transaction processes, the user could get a much worse swap.

**Proof of Concept:**
1. The price of WETH right now is 1,000 USDC
2. User inputs a `swapExactOutput` 
   1. inputToken = USDC
   2. outputToken = WETH
   3. outputAmount = 1
   4. deadline = ...
3. The function does not offer a maxInput amount
4. As the transaction is pending in the memepool, the market changes! and the price moves HUGE -> 1 WETH is now 10,000 USDC. 10x more than the user expected.
5. Finally, the transaction completes, but the user sent the protocol 10,000 USDC for 1 WETH instead of 1,000 USDC.

**Proof Of Code**

<details>
<summary>Code</summary>

Add the following to the `TSwapPool.t.sol` test file

```javascript
    function test_swapExactOutput_noSlippageProtection() public {
        address attacker = makeAddr("attacker");

        uint256 WETH_AMOUNT = 1_000e18;
        uint256 POOL_TOKEN_AMOUNT = 1_000_000e18;

        // Give liquidity provider enough to add liquidity
        weth.mint(liquidityProvider, WETH_AMOUNT);
        poolToken.mint(liquidityProvider, POOL_TOKEN_AMOUNT);

        // 1. addLiquidity of 1_000e18 WETH and 1_000_000e18 USDC
        // This means currently, 1 WETH (outputToken) is worth 1000 USDC(poolToken / inputToken)
        vm.startPrank(liquidityProvider);
        weth.approve(address(pool), WETH_AMOUNT);
        poolToken.approve(address(pool), POOL_TOKEN_AMOUNT);
        pool.deposit(WETH_AMOUNT, WETH_AMOUNT, POOL_TOKEN_AMOUNT, uint64(block.timestamp));
        vm.stopPrank();

        // 2. Record how much USDC the victim "expects" to pay for WETH right now
        // We cant use `getInputAmountBasedOnOutput` because it is bugged
        uint256 victimDesiredOutputAmount = 10e18; // User wants exactly 10 output tokens (Weth)
        uint256 inputReservesBefore = poolToken.balanceOf(address(pool));
        uint256 outputReservesBefore = weth.balanceOf(address(pool));
        uint256 victimExpectedInputAmount = ((inputReservesBefore * victimDesiredOutputAmount) * 1_000)
            / ((outputReservesBefore - victimDesiredOutputAmount) * 997);
        console.log("Victim expects to pay: ", victimExpectedInputAmount); // at least 10_131.404313951956880743 USDC

        // 3. Attacker front-runs, moves the price drastically
        uint256 attackerInputAmount = 200_000e18;
        uint256 minOutputAmount =
            pool.getOutputAmountBasedOnInput(attackerInputAmount, inputReservesBefore, outputReservesBefore);
        vm.startPrank(attacker);
        poolToken.mint(attacker, attackerInputAmount);
        poolToken.approve(address(pool), attackerInputAmount);
        pool.swapExactInput(poolToken, attackerInputAmount, weth, minOutputAmount, uint64(block.timestamp));
        console.log("Attackers current WETH balance: ", weth.balanceOf(attacker)); // 166.249791562447890611 WETH
        vm.stopPrank();

        // 4. Record how much USDC the victim will actually pay for WETH after price movement
        // We cant use `getInputAmountBasedOnOutput` because it is bugged
        uint256 inputReserversAfter = poolToken.balanceOf(address(pool));
        uint256 outputReservesAfter = weth.balanceOf(address(pool));
        uint256 victimActualPaidInputAmount = ((inputReserversAfter * victimDesiredOutputAmount) * 1_000)
            / ((outputReservesAfter - victimDesiredOutputAmount) * 997);
        console.log("Victim actually paid: ", victimActualPaidInputAmount); // at least  14_611.356940114660006422 USDC

        assertGt(victimActualPaidInputAmount, victimExpectedInputAmount);
    }    
```

Since the function don't allow for the user to set a limit (`maxInputAmount`), they take whatever price is set.

### [H-3] `TSwapPool::sellPoolTokens` mismatches input and output tokens causing users to receive the incorrect amount of tokens

**Description:** The `sellPoolTokens` function is intended to allow users to easily sell pool tokens for WETH. Users indicate how many pool tokens they willing to sell in the `poolTokenAmount` parameter. However, the function currently miscalculates the swapped amount.

This is due to the fact the the `swapExactOutput` function is called whereas the `swapExactInut` function should be called. Because users specify the exact amount of input tokens, not output.

**Impact:** Users will swap the wrong amount of tokens which is a severe disruption of protocol functionality.

**Proof of Concept:**

**Recommended Mitigation:** Consider chainging the implementation to use, `swapExactInput` instead of `swapExactOutput`. Note that this will also require changing the `sellPoolTokens` function to accept a new parameter (ie., `minWethToReceive`) to be passed to `swapExactInput`.

```diff
    function sellPoolTokens(
        uint256 poolTokenAmount
+       uint256 minWethToReceive
        ) external returns (uint256 wethAmount) {
-       return swapExactOutput(i_poolToken, i_wethToken, poolTokenAmount, uint64(block.timestamp));
+       return swapExactInput(i_poolToken, poolTokenAmount, i_wethToken, minWethToReceive, uint64(block.timestamp));
    }
```

Additionally, it might be wise to add a deadline to the function, as there is none currently.

### [H-4] In `TswapPool::_swap` the extra tokens given to users after every `swapCount` breaks the protocol invariant of `x * y = k` 

**Description:** The protocol follows a strict invariant of `x * y = k`. Where:
- `x`: The balance of the pool token
- `y`: The balance of WETH
- `k`: The constant product of the two balance

This means, that whenever the balances change in the protocol, the ratio between the two amounts should remain contant, hence the `k`. However, this is broken due to the extra incentive in the `_swwap` function. Meaning that over time the protocol funcds will be drained.

The following block of code is responsible for the issue.

```javascript
    swap_count++;
        if (swap_count >= SWAP_COUNT_MAX) {
            swap_count = 0;
            outputToken.safeTransfer(msg.sender, 1_000_000_000_000_000_000);
        }
```

**Impact:** A user could maliciously drain the protocol of funds by doing a lot of swaps and collecting the extra incentive given out by the protocol.

Most simply put, the protocol's core invariant is broken.

**Proof of Concept:**
1. A user swaps 10 times, and collects the extra incentive of `1_000_000_000_000_000_000` tokens
2. That user continues to swap until all the protocol funcds are drained.

<summary>Proof Of Code</summary>

place the following into `TSwapPool.t.sol` test file

```diff
-           swap_count = 0;

-       }
```

## Medium

### [M-1] `TSwapPool::deposit` is missing deadline check causing transaction to complete even after the deadline

**Description:** The `deposit` function accepts a `deadline` parameter, which according to documentation, transaction must have been completed before the deadline. However, this parameter is never used. As a consequence, operation that add liquidity to the pool might be executed at unexpected times, in market conditions where the deposit rate is unfavourable.

**Impact:** Transactions could be sent when market conditions are unfavourable to deposit, even when adding a deadline parameter

**Proof of Concept:** The `deadline` parameter is unused

**Recommended Mitigation:** Consider making the following change to the function.

```diff
    function deposit(
        uint256 wethToDeposit,
        uint256 minimumLiquidityTokensToMint,
        uint256 maximumPoolTokensToDeposit,
        uint64 deadline
    )
        external
+       revertIfDeadlinePassed(deadline)
        revertIfZero(wethToDeposit)
        returns (uint256 liquidityTokensToMint)
    {
```

## Low

### [L-1] `TSwapPool::_addLiquidityMintAndTransfer` emits event with wrong order of Parameters

**Description:** When the `LiquidityAdded` event is emitted in the `TSwapPool::_addLiquidityMintAndTransfer` function, it logs values in an incorrect order. The `poolTokenToDeposit` value should go in the third parameter's position, whereas the `wethToDeposit` value should go second.

**Impact:** Event emission is incorrect, leading to off-cahin function potentially malfunctioning.

**Recommended Mitigation:**
```diff
-   emit LiquidityAdded(msg.sender, poolTokensToDeposit, wethToDeposit);
+   emit LiquidityAdded(msg.sender, wethToDeposit, poolTokensToDeposit);
```

### [L-2] Default value returned by `TSwapPool::swapxactInput` result in an incorrect return value given 

**Description:** The `swapExactInput` function is expected to return the actaul amount of tokens bought buy the caller. However, while it declares the named return value `output` it is never assigned a value, nor does it use an explicit return statement. 

**Impact:** The return value will always be 0, thereby giving an incorrect information(the amount of tokens they get) to the caller.

**Recommended Mitigation:**

```diff
    {
```

### [I-3] `PoolFactory::createPool` should use `.symbol()` instead of `.name()`

**Description:** When deriving the symbol for a liquidity token, it's best to concact `ts` (representing T-SWAP) with symbol of the underlying pool token (e.g ARB for Arbitrum) and not the full name of the token.

### [I-4] Event is missing `indexed` fields

**Description:** Index event fields make the field more quickly accesible to off-chain tools that parse events. Each event should use three indexed fields if there are three or more fields, and gas usage is not particularly of concern for the events in question.

```diff
-   event Swap(address indexed swapper, IERC20 tokenIn, uint256 amountTokenIn, IERC20 tokenOut, uint256 amountTokenOut);
+   event Swap(address indexed swapper, IERC20 indexed tokenIn, uint256 indexed amountTokenIn, IERC20 tokenOut, uint256 amountTokenOut);
```

### [I-8] No natspec in `TSwapPool:swapExactInput`

**Recommended Mitigation:** Provide a detailed natspec for the `swapExactInput` function.

```diff
+       external
-       public

        revertIfDeadlinePassed(deadline)
        returns (uint256 output)
    {
```
